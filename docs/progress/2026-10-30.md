## The mechanism

A per-frame log of what the renderer put in (uploads, sections added to
or removed from the drawn set) around each band: a drawn real section
gets a mesh with the new chunk row; the preview sections over that row
leave one or two frames later, by the selection or a mesh swap. Both seas
draw there meanwhile and the translucent pass blends them lighter
(ADR-100 has the details and the two rules that failed).

Two attempts measured and dropped on the way: grouping a real section's
mesh with its neighbors' (no effect, taken out of the code); the column
watch's "real and preview over each other" state alone (the preview keeps
quads over real columns legitimately for long, so it does not single out
the bands; kept as a state of the watch).

## D.2: the preview's ground from the surface rules (ADR-101)

The surface rules of the generator (vanilla, Biomes O' Plenty, Terralith
through TerraBlender and Lithostitched) run on one column per 4-block
cell of each stand-in chunk; the tile keeps that column's top and filler,
and the features grow on it.

Verified with `/farfield spike surface <biome>` on a NeoForge dev server
with the user's worldgen mods (a fresh world), 8 x 8 chunks each, real
heights:

| Biome | Ruled column right | Guess right (cells) |
|---|---|---|
| biomesoplenty:redwood_forest | 99.9 % | 28.8 % |
| biomesoplenty:tropics | 98.2 % | 67.7 % |
| terralith:desert_canyon | 99.9 % | 47.9 % |
| terralith:volcanic_peaks | 100 % | 77.4 % |
| minecraft:badlands | 99.8 % | 79.0 % |
| minecraft:snowy_slopes | 99.5 % | 66.4 % |
| minecraft:deep_ocean | 99.5 % | 0 % |
| minecraft:plains | 100 % | 58.1 % |

Cost 1.7 to 4.9 ms a chunk once cut to one column a cell (4.6 to 9.6 ms
for all columns; a JFR profile pointed at the rules and the heightmaps);
whole tiles 6.0 and 6.3 s, of which 2.0 and 2.4 s are the surface. A
first run read the block under the top in every column (the spike's
plains "dirt" gave it away) and was fixed before these numbers. In a dev
client over the spike world at noon: podzol under the redwoods, lavender,
terracotta, red and white sand in the badlands. `gradlew build` passes.
The dev server is back as it was (worldgen jars in `mods-worldgen/`,
`server.properties` restored, the spike worlds deleted).

Not verified: the user's pack on their server (every tile is built again

## Deploys through one script

D.2 deployed (the user's yes; the server was off, so the jar only): sha256
`7b102a55…` on the server's `mods` and in the pack instance, old jars in
the server's `/tmp` and beside the instance's `mods`.

The user asked for a gitignored skill with a script, so the deploy checks
are not redone by hand each time. `farfield-deploy` (machine-local, in
`.gitignore`; it absorbs the former `farfield-home-server-deploy`) runs
`deploy.sh --status | --server | --client [--build]`: the jar against the
sources, the instance's game, the container's state (a running server is
stopped, the jar copied, started again and its `Done` line awaited; an off
one stays off), backups, hash and one-jar checks, and a
`farfield-deployed.txt` stamp on both sides whose protocol the next run
compares. Verified: `--status`, a client deploy of the same jar, the
refusal on sources newer than the jar. Not run yet: stopping and starting
a running server (the server was up and in use).
