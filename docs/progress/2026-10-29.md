## The analysis method, as the user pointed out

The first pass over the user's recording looked for sky-coloured pixels
and frame-to-frame change spikes: it found the 2 to 3 frame hole at the
game's render edge (frames 336 to 338, 576 to 577) but none of the bands
nor the one-frame level-2 areas (frames 286, 294) the user then had to
annotate. Reusing it would miss them again. Better: a "flash" detector
(a zone that changes and comes back, frame N against N-1 and N+1),
validated first against the user's 18 annotated frames
(`<Videos>/farfield-frames-231234`, frames 1 to 350); and a detector in
the renderer that logs chunk columns whose drawn state (preview, real
level) changes and reverts within 3 frames.

## Agent playtesting, step 1: the agent inbox (ADR-095)

`docs/analysis/agent-playtesting.md` surveyed what lets an agent test like
a player (MCP mods, loader test frameworks, headless clients, bots, image
diff). A second pass added a review: a replay needs fresh terrain, the
open bug is pack-only, an engine-state oracle can be blind to a
Sodium/Iris fault, the planned validation on the annotated video cannot
run an in-engine detector, and replays are not deterministic. Revised
order: inbox, pack instance, flight replay, frame detector, CI.

Step 1 done: `AgentClient` runs command files from
`<game dir>/farfield-agent/inbox/` with `-Dfarfield.agent=true` (set by
both dev client runs): chat commands, absolute teleports, look,
framebuffer screenshots, state, `wait stable`, waits, quit; one JSON
reply per command in `outbox.jsonl`. The `farfield-dev-client-check`
skill describes it.
