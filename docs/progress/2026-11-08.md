## Done

- The user asked whether ADR-118 changed performance. Tile builds did not
  move (2.9 to 4.5 s per tile before and after, noise from the spot), but
  the client's preview mesh jobs had become 3 to 10 times slower: the
  pack logs of 2026-11-07 at -925, 120, 1390 read 1.3 to 3 ms per job before
  ADR-118 and 6 to 26 ms after, 35 ms on a full remesh (the preview light
  switch) against 2.8 to 5.2 ms before.
- Cause: `PreviewVoxels.dig` read the lakes through the raw tile source,
  not the section's tile cache. On the client that source is
  `PreviewStore.read`, a shared lock and an LRU lookup per call, and it ran
  1 to 4 times per column on the finest level, up to 64 times on coarser
  ones (16 samples, up to 4 tiles each), for every tile holding a lake (most
  of them).
- Fix: `PreviewVoxels.NearTiles`, the tiles of the section's area (its
  columns, one voxel beside, the features' margin), each looked up once on
  first use; `dig` reads through it. Regression test
  `PreviewTest.aSectionLooksUpItsTilesAFewTimesNotOncePerColumn`: 88 to 233
  source reads per section on levels 0 to 4 with the fix, 2,685 on level 0
  without it (the test fails then, checked by swapping the argument back).

## Memory: the Fabric pack with and without Farfield (agent runs, 18:30-18:50)

The user asked whether the LODs and the preview are what makes the game's
memory blow up. Two runs of the Fabric pack in production (`-Xmx8G`,
854x480, no shader pack, fresh test world, idle at the spawn, then with
Farfield two far teleports), `FARFIELD_WITHOUT=1` for the baseline (new in
`dev/agent/fabric-prod-client.py`), native memory tracking on, the
window minimized and `pauseOnLostFocus` off on both sides. A first
baseline run was dropped: it opened over the user's windows and paused.

| Sample | Commit without | Commit with | Heap committed without / with |
|---|---|---|---|
| 60 s | 4,721 MB | 5,330 MB | 2,736 / 3,048 MB |
| 180 s | 5,191 MB | 5,807 MB | 2,736 / 3,364 MB |
| 300 s | 4,720 MB | 5,584 MB | 2,736 / 3,364 MB |
| After the teleports | - | 5,704 to 5,778 MB | - / 3,576 MB |

- Farfield adds about 0.6 to 1.0 GB of commit (12 to 20 %): live heap
  after a full GC 1,696 against 1,456 MB (+240 MB, mostly int and long
  arrays), the G1 heap grown by 0.3 to 0.8 GB more (allocation churn of
  the preview and the meshing; inside `-Xmx`), and 0.1 to 0.3 GB of native
  memory outside the heap.
- Outside the heap the game holds about 2.0 to 2.45 GB with or without
  Farfield (metaspace 0.23 GB, code 0.12, GC 0.12, and about 1.4 GB the JVM
  does not track: the driver, LWJGL, the mods' natives).
- So on this pack Farfield is not the cause of a game far above its
  `-Xmx`. The NeoForge crash (17 GB for an 8 GB heap, about 8 GB native)
  is not explained by these numbers; not measured: NeoForge, a shader pack,
  the user's resolution (3840x2019), the quad buffer grown to 256 MB by a
  spyglass zoom.
- The user's idea from this run: plan item F.1, the agent harness as a mod
  of its own (a baseline without Farfield then keeps it).
