# Progress — 2026-10-14 (project bootstrap)

Farfield starts here. The decision to leave Neo-Voxy (a fork of Voxy, whose
license forbids redistribution) was taken today after a state-of-the-art
analysis and a Q&A, both done in the Neo-Voxy repository; Neo-Voxy was closed
at 1.4.0 the same day.

## Commits

- chore — bootstrap: MultiLoader skeleton, docs, ADRs, CI
- docs — first CI run green
- docs — reference world corpus (A.8)

## Decisions

The Q&A outcomes are recorded as ADR-001 to ADR-016 in `docs/DECISIONS.md`.
Highlights: 1.21.1 first with 26.x/Vulkan planned from the start; NeoForge +
Fabric; engine core in pure Java (`api`, `core`) separate from Minecraft code
(`common`); GPU-driven raster renderer on OpenGL 4.6 first; 3D paletted
bricks with a mip pyramid; storage format chosen after spike S1; surface-only
LOD streaming by default under a strict bandwidth budget; zero-config shader
packs as a goal; package `io.lakio.farfield`; license deferred, repository
private.

Also decided: Krios conventions, everything in git in English, and a
`Co-Authored-By` trailer on commits written by Claude (Krios had dropped it;
the user prefers to keep it).

## Spike S5 — region-file import (M1.B)

### Commits

- feat(core) — pure-Java Anvil reader, chunk decoder and import pipeline
  (spike S5), with its benchmarks and docs

### Done

- `core.nbt`: `NbtReader`, a bounds-checked forward cursor over binary NBT
  (read the needed fields, skip the rest, no tag tree, depth limit 512).
- `core.anvil`: `RegionFile` (header, sectors, external `.mcc` chunks),
  `ChunkDecompressor` (zlib, gzip, none, LZ4), `Lz4BlockStream` and
  `XxHash32` written from the format descriptions (no dependency),
  `ChunkDecoder` (1.18+ format: header, then sections on demand; block-state
  palettes with canonical keys `name[k=v,...]`, packed indices, biomes, light;
  corrupt data raises warnings or a format exception, never anything else),
  `KeyRegistry` (thread-safe key to id), reusable `ChunkData`/`SectionData`.
- `core.importer`: `RegionImporter` (one worker per region, nearest first;
  sink on the worker thread for backpressure; shared chunks/s throttle;
  pause/resume/cancel; `ImportCheckpoint`, append-only and fsynced per
  region, keyed by file name, size and mtime), `ImportStats` (counters,
  per-stage worker time, status/data-version/compression histograms).
- Benchmarks in `core/src/jmh`: `ChunkDecodeBenchmark` (JMH, per chunk) and
  `ImportBenchmark` (end to end, `gradlew :core:importBench --args=...`,
  pinned to the Java 21 toolchain).
- ADR-017 (region-file import), status **proposed**.
- `docs/corpus.md`: generation status per world, and two corrections (below).

### Validated

- `:core:test`: 34 tests green (NBT reader, LZ4/XXH32 against lz4-java,
  decoder incl. palette bit widths 4/5/8/9/12, canonical keys, light,
  legacy and corrupt input with fuzzing, region files with every
  compression type and an external chunk, importer: counts, checkpoint
  resume, truncated checkpoint, throttle, pause, sink failure).
- Every chunk of the 8 corpus worlds and of the user's server overworld
  decodes with **0 errors and 0 warnings**. All zlib, no `.mcc`.

### Numbers (16 logical cores, JDK 21.0.10)

End to end, `importBench`, chunks/s handed to the sink (full chunks only),
second run (warm OS cache; first runs are within ~10 %):

| World | Full chunks | 1 thread | 8 threads | 16 threads |
|---|---|---|---|---|
| `server-pregen` | 20,305 | 7,017 | 43,168 | 57,779 |
| `modded-large` | 51,752 | 5,417 | 35,842 | 47,852 |
| `modded-played` | 19,894 | 5,547 | 33,806 | 46,087 |
| `main-install` | 72,873 | 7,107 | 46,776 | 61,359 |
| `amplified` | 4,225 | 5,430 | 17,490 | 17,551 |
| `server-spawn` | 36,864 | 6,776 | 43,127 | 52,759 |
| `server-dense` | 16,384 | 6,675 | 40,178 | 58,717 |

`amplified` has 16 regions with its full chunks in a few of them, so it
stops scaling at 8 threads (one region per worker). `dh-baseline-1.20.1` is
not meaningful for throughput (0.8 % full chunks, see `docs/corpus.md`).

User's server overworld, read in place from `D:` (cold cache), 8 threads:
2,092 regions, 17.5 GB, 1,507,797 chunks read, 1,331,683 imported in
**42.4 s: 31,417 chunks/s imported, 331 MB/s** of compressed data. Worker
time per chunk: read 50 µs (disk), decompress 109 µs, decode 71 µs.

JMH, one thread, µs per full chunk of the largest region of the world:

| World (region) | decompress | decode | both |
|---|---|---|---|
| `server-spawn` (r.0.1, 1,024 chunks) | 73.8 | 36.7 | 108.5 |
| `server-pregen` (r.-1.-1, 796 chunks) | 87.7 | 33.8 | 120.9 |
| `amplified` (r.0.-1, 1,024 chunks) | 137.2 | 77.5 | 213.3 |

**Exit criterion (> 2000 chunks/s on 8 cores) met**: 8.7x on `amplified`
(region-bound, see above), 17x to 23x on the other worlds, 15.7x on the
cold 17.5 GB server import. zlib inflation is about two thirds of the
cost; the decoder itself is 35 to 80 µs per chunk.

### Corrections

- The user's server overworld has **1,507,797** chunks, not 1,926,613 as
  written above and first in `docs/corpus.md` (confirmed by an independent
  count of non-empty location entries).
- `dh-baseline-1.20.1` is 99 % proto-chunks (`structure_starts`): its
  region size is mostly sector padding, so its LOD/region ratio is not
  comparable.

### Not verified

- LZ4 (type 4), gzip and external `.mcc` chunks only on synthetic data: no
  corpus world uses them.
- Pre-1.18 chunks: detected and skipped, not decoded (none in the corpus).
- Modded worlds with non-standard heights: decoded generically (section Y
  is read, not assumed), but no such world in the corpus.
- No game command calls the importer yet; nothing runs inside Minecraft.

## Spike S2 — meshing (M1.C)

ADR-017 accepted by the user.

### Commits

- feat(core) — LOD sections in paletted bricks and binary greedy meshing
  (spike S2), with its benchmark and docs

### Done

- `core.lod.LodSection`: 32³ voxels as 4x4x4 bricks of 8³, one palette per
  section (material ids), uniform bricks with no data, non-uniform bricks
  bit-packed at 1/2/4/8/16 bits; palette growth repacks; `writeChunkSection`
  fills an octant from a decoded `SectionData` (a chunk section is exactly
  2x2x2 bricks).
- `core.mesh`: `BinaryGreedyMesher` (X rows of opaque/translucent bits from
  the bricks, Y and Z columns by 32x32 bit transposes, face culling per
  column with neighbor border bits, transposes into per-depth planes, split
  by material, greedy merge with bit runs), `Quad` (8-byte packing),
  `MeshBuffer` (per-direction groups), `MaterialClassifier`.
- `MeshBenchmark` (JMH): every non-empty 32³ section of the largest region of
  a world, with its real neighbors; block keys classified by a rough
  bench-only heuristic (air and small plants, water/glass/ice translucent,
  the rest opaque cubes).
- JMH Gradle options: `-PjmhIncludes=<regex>`, `-PjmhProfilers=gc,stack`.
- ADR-018 (CPU binary greedy meshing, 8-byte quads), status **proposed**.

### Validated

- `:core:test`: 46 tests green, of which 12 new: transpose against a naive
  one, `LodSection` (bit widths, 60,000 random writes across repacks,
  compaction, chunk-section octants), mesher (single voxel, solid section
  with and without opaque neighbors, sea floor under water, border planes,
  and 60 random sections checked face by face against a brute-force
  visibility oracle: every visible face covered exactly once with its
  material, no hidden face drawn).

### Numbers (one thread, JDK 21.0.10)

| World (region) | Sections with quads | Mesh time | Quads / section | Faces / quad | Quad bytes | Brick bytes |
|---|---|---|---|---|---|---|
| `server-spawn` (r.0.1) | 1,045 of 3,072 | 138.0 µs | 1,176 | 4.3 | 9,410 | 24,212 |
| `server-pregen` (r.-1.-1) | 1,002 of 2,460 | 121.9 µs | 1,196 | 3.0 | 9,567 | 18,330 |
| `amplified` (r.0.-1) | 2,035 of 3,072 | 137.4 µs | 1,286 | 1.9 | 10,285 | 22,839 |

- **Exit criterion (< 200 µs per 32³ section) met**, with 30 to 40 % margin.
- Allocation per mesh: 0.4 B (`gc` profiler), i.e. none.
- Stack sampling: no single hotspot (building rows, splitting by material,
  transposes and greedy merge each take 10 to 13 % of samples).
- Building `LodSection`s from decoded chunks: 6.6 to 12 µs per chunk section.
- Sections are meshed with caves (full data); the surface-only default of
  ADR-013 will mesh less.

### Not verified

- Light and AO: not computed, not part of the merge key. Adding them will
  lower the merge ratio and add cost; the 30 to 40 % margin is what is left.
- Material classes come from a key heuristic in the benchmark only; the real
  classification (block states, render layers) is Minecraft-side work.
- Non-cube blocks (slabs, stairs, plants) are drawn as full cubes or not at
  all; no rendering yet, so no visual check.
