## Face directions (E.12)

Before: one indirect command per section and pass with all its quads; the
rasterizer culled back faces after the vertex shader had run on them.

Now each section's quads are stored in 12 groups (opaque by direction,
then translucent by direction; `Resident.groups`), and the draw loop emits
one command per run of adjacent groups whose direction can face the camera
(`FaceDirections.front`, core: +X faces only when the camera is past the
box's min X, with one block of slack). No shader change: `gl_VertexID`
starts at the command's `first`, as the translucent pass already relied on.
The stat line now says `N of M quads sent (face directions)`.

## Depth pre-pass (E.13, ADR-043)

The user asked to go after the per-pixel cost. Opaque faces now draw in
two passes: a depth-only pre-pass (`lod.frag` with `DEPTH_ONLY`: hand-off
and cutout discards only, color writes off), then the shaded pass with
`layout(early_fragment_tests)` (`EARLY_Z`), `GL_EQUAL`, no depth writes
and no discard. The translucent pass uses the `EARLY_Z` program with its
discards (it writes no depth). `GlProgram` takes `#define` lines;
`LodRenderer.Shader` holds each variant's uniform locations and `use()`
sets them. `invariant gl_Position` in `lod.vert`. The GPU time is split
per pass on the stat line (four timestamps per frame).
`/farfield debug prepass on|off` switches the pre-pass, not saved.

Verified in the Fabric dev client (same view, one run):

|---|---|---|---|---|

- Three programs compile and link (no `cannot compile`, `LOD renderer

line after each switch:

| Pre-pass variant | Pre-pass time |
|---|---|
| As in ADR-043 | 810 to 817 us |
| Vertex work only (`GL_RASTERIZER_DISCARD`) | 345 us |
| No discard at all (early tests) | 474 us |
| Hand-off discard only, no cutout test | 560 us |

Then, in a second run with a lighter pre-pass (texture read only for faces
with holes, hand-off lookup only near the game's grid, vertex outputs cut
under `DEPTH_ONLY`): 774 to 781 us, against 456 for the same build without
discard. The vertex cut changed nothing (345 us again). The discard itself
was the cost, so the pre-pass now splits sections in two lists (ADR-044):
`SOLID` (no discard) first, then the sections that overlap the game's grid
or have opaque faces with holes. `MaterialColors.CUTOUT` marks faces whose
baked texture has a texel under half coverage; `MaterialColors.cutout`
reads it per material from the mesher threads (true until built), and
sections meshed before the table was complete are meshed again.

Third run, same view:

## Ice and water at the preview border (E.11, ADR-045)

The user noticed during the dev client runs, at the border between real
LODs and the noise preview, water that seemed to "enter" the ice, and that
the preview should freeze the sea's top layer in frozen biomes.

Found, in this order (Fabric dev client, `farfield-test`, views from
`/tp @s 48 180 32 45 25` and `/tp @s 48 90 32 50 8`):

1. The preview never froze: one water material up to the sea. Now a
   frozen bit per 4-block cell (vanilla's freeze_top_layer test with the
   cell's own biome at the sea's top block), tile format 4, ice on the
   voxel holding the sea's top block (ADR-045). First version used the
   chunk's biome: no visible difference at the spot checked, kept the
   per-cell rule as vanilla's. Unit test `frozenCellsTopTheSeaWithIce`.
   In game: the preview's frozen ocean shows ice with open-water patches
   like the real one beside it.
2. Real water drew walls toward chunks without data (a stored section
   covers 4 chunks or more; missing ones read as air). Real sections now
   treat empty columns and missing horizontal neighbors as solid for
   translucent faces (`BinaryGreedyMesher.setEmptyColumnsUnknown`,
   `addEmptyColumns`, unit test `emptyColumnsHideWaterWallsWhenUnknown`).
   No visible change at the spots checked: the walls seen without the
   preview were opaque ground cross-sections.
3. The dark rectangle the user saw: the opaque edge wall of real terrain,
   seen through the preview's ice and water where the real sea floor is
   above the preview's estimate. The gap between two loaded areas is a
   strip of border chunks (status `initialize_light`, read from the region
   files): generated, not ingested. Options given (ingest border chunks
   with estimated light, or raise the preview's border columns to the real
   floor); the user chose to leave it for later.
4. Black holes at the vanilla edge with the camera high: vanilla's section
   graph never draws a section more than the render distance (in
   sections) above or below the camera's section
   (`SectionOcclusionGraph.getRelativeFrom`), but `lod.frag` gave way
   anyway. The vanilla rule now has that vertical limit. Checked at
   y 180 and 240: no hole, no double ice.

Frame rate: the user pointed out the 120 fps default cap. `maxFps:260`
(vanilla's "Unlimited": `Minecraft.java` limits only below 260) and
