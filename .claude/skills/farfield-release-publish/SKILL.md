# Farfield release publish

Before tagging, list the GitHub issues the user said he will answer himself once he has tested (`gh issue list`, then his own words in the session or memory). Remind him they are pending and offer drafts; never post the replies unasked.

A release is a pushed tag `v<version>[-alpha.N]`. Do not tag until the user says every feature planned for the release is complete: finishing one work item is not a reason to tag. `.github/workflows/release.yml` builds both loader jars and publishes them. Never publish by hand, and never report a platform as published without its log line.

1. Check `version=` in `gradle.properties` is the core of the tag (`0.1.0` for `v0.1.0-alpha.1`). A mismatch stops the Prepare job before any upload. Pick the bump from what changed since the last tag: a stream protocol version change makes it a minor bump (0.2.1 to 0.3.0), since servers and clients of different versions cannot stream; only same-protocol fixes are a patch.
2. Check the ci-workflows PR that provides `publish-mod.yml@v1` is merged, and that the variables `MODRINTH_ID`, `CURSEFORGE_ID` and the secrets `MODRINTH_TOKEN`, `CURSEFORGE_TOKEN` exist (`gh variable list`, `gh secret list`). Missing ones: use the `git-github-config` skill.
3. Lint the workflows before tagging: `actionlint .github/workflows/*.yml`. actionlint is not on PATH on this machine; use `uvx --from actionlint-py actionlint .github/workflows/*.yml` (it passed on 0.2.0). Also check the `targets` JSON offline before tagging, since the release workflow runs only on a tag: parse `release.yml` with PyYAML, `json.loads` the `jobs.publish.with.targets` string, assert the `version-suffix` values are unique, and glob each target's `files` pattern against the jars already built in `neoforge/build/libs` and `fabric/build/libs`. Run the script with plain `python`, not `python -I`: isolated mode hides the user site-packages where PyYAML is installed (`ModuleNotFoundError: No module named 'yaml'`). For a new game version, `https://api.modrinth.com/v2/tag/game_version` lists whether Modrinth knows it (CurseForge needs its token, so its list stays unchecked). Then sweep the user-facing text for claims the release changes: `grep -rn -i "1\.21\|NeoForge and Fabric" docs/VISION.md README.md CLAUDE.md` catches version and loader claims a port left behind (the 1.20.1 port left two `VISION.md` lines false: the "NeoForge and Fabric" line and the "older than 1.21.1" non-goal), the README's Minecraft and loader table, the lang files' tooltips (`en_us.json` and `fr_fr.json`, where a stale "Single player only" survived until 0.2.0), `docs/listing/description.md`, the README status line, the README's body sentences (not only its status line), the plan link, and `version=` in `gradle.properties`.
   Check every numeric claim (distances, limits, mod or pack counts, protocol numbers) against the constant that enforces it, e.g. `grep -rn "MAX_" core/src/main common/src/main`, not against the previous listing text: the 0.3.0 listing and README said "up to 4,096 blocks" while the code allowed the world border (`MAX_RADIUS`, `MAX_FOG_DISTANCE`).
4. Tag the merged head of `main`, not the local branch: `git fetch -q origin`, check the remote's version with `MSYS_NO_PATHCONV=1 git show origin/main:gradle.properties | grep "^version="`, then `git tag vX.Y.Z-alpha.N origin/main && git push origin vX.Y.Z-alpha.N`.
5. Watch the run: find it by its tag, not the newest run, and poll until it appears: `gh run list --workflow release.yml --limit 5 --json databaseId,headBranch --jq "[.[] | select(.headBranch == \"TAG\")][0].databaseId"`. Then `gh run watch RUN_ID --exit-status --interval 30` inside a background script that also prints the jobs, the publish lines and the GitHub Release, so the wait does not block the session.
6. Verify, in this order: five jobs green (Prepare release, Build mod, GitHub Release, Publish NeoForge, Publish Fabric), e.g. `gh run view RUN_ID --json jobs --jq '.jobs[] | "\(.name): \(.conclusion)"'`; each Publish job logs `Successfully published the assets to CurseForge, Modrinth` (`gh run view RUN_ID --log | grep -a "Successfully published"`); the log line `version-type: release|alpha|beta` matches the tag; `gh release view TAG --json name,isPrerelease,assets` lists both jars, and `isPrerelease` is true only for alpha and beta.
7. The Modrinth public API returns 404 for an unlisted, unapproved project. The token-authenticated `GET /project/{id}/version` returns 404 too while the project is `processing` (seen on 1.2.0, 2026-11-24), so the token cannot confirm the uploaded files either; only the page read back by the user can. Modrinth and CurseForge pages stay unverified: ask the user to check loaders, game version, dependencies. Say so in the report.
8. A Modrinth 401 on the step that removes the featured flag from the previous versions (it ran after the files upload) made the 1.2.1 run red with every jar published. ci-workflows v1.0.18 (2026-11-28, under `@v1`) passes `modrinth-unfeature-mode: none`, so mc-publish skips that step; not yet seen in a release run. Never re-run a red Publish job whose upload went through: CurseForge would take the jar twice. Read the uploaded versions with the token of `docs/listing/modrinth.py` (`GET /project/<id>/version`).
9. Log the release in the day's `docs/progress` file (session wrap-up skill). After a rebase merge of the release PR, the PR's commits carry new hashes on `main`: the log names the commit the tag points to on `main`, and notes that the PR's hashes differ. The GitHub Release body defaults to the commit list: prepend a readable summary with `gh release edit TAG --notes-file FILE`, where FILE holds the summary followed by the old body from `gh release view TAG --json body --jq .body`.
10. Jars built from `main` after a release keep the published version in their names (`farfield-neoforge-1.21.1-1.2.1.jar` built at a later commit is not the published 1.2.1). When handing such a jar to the user for a test, say in the handoff which commit it holds and that it is not the published file. Put the commit in the progress log too, next to the jars' names.

Several Minecraft versions (Farfield ships 1.21.1 and 1.21.11, NeoForge and Fabric): `publish-mod.yml` takes one `game-versions` list for every target and names each Modrinth version `<version>+<loader>`, so two NeoForge jars collide. Each target of the `targets` JSON then needs its own `game-versions` and a `version-suffix` (e.g. `neoforge-1.21.11`). Since ci-workflows v1.0.14 (PR #10, merged 2026-11-19, under `@v1`) the fields exist, and Farfield's `release.yml` has twelve targets (NeoForge and Fabric, for 1.21.1, 1.21.11, 26.1.2, 26.2 and 26.3; suffixes `<loader>-<mc>`), plus 1.20.1 on Forge (`forge-1.20.1`, Java 17, the file also tagged for NeoForge, ADR-177) and Fabric. The Forge jar must be copied to `forge/build/libs`: the reobfuscated jar the legacy plugin writes to the node's own folder is where the release does not look, so check the jar's folder in the build output before tagging. The 26.x targets carry `"java-versions":"25"` (ADR-171); the 1.21.x targets keep the workflow input `java-versions: 21`, because the shared workflow reads `matrix.target.java-versions || inputs.java-versions` per target. A new Minecraft version gets two more targets there, with its own Java version if it differs. The workflow's `Check the targets` step fails before the build on a missing game version or a repeated suffix.

Details, run ids and warnings: see `references/release-checklist-details.md`.

## Store listing text and gallery

Listing text states only what the released build does today. Anything planned goes under "Not there yet", never in the feature list. Check each feature claim in the code and the lang files first: a stale claim is worse than a missing one.

- Source: `docs/listing/description.md` (English). It names no Minecraft or Farfield version (the user, 2026-11-19: the versions shipped and the stores' filters say which Minecraft versions are supported); keep it so. One line per paragraph and per list item, never hard-wrapped (since 2026-11-19): CurseForge's Markdown editor takes every newline as a line break and breaks list items' indented continuation lines, and the user pastes the same text on both stores; edit it keeping each paragraph on its own line. The README links to it: change both when a feature lands or is dropped. Re-check "Not there yet" on each release.
- The README status line states the version and what is planned, never "private" or "early development" once the repo is public.
- Banners: `python docs/brand/render_banners.py` regenerates `banner-scene.png` and `banner-icon.png` (the icon comes from `docs/brand/render_logo.py`). Open each PNG before use.
- Screenshots cover the biomes the mod is about, not one biome: badlands, desert, savanna, dark forest, mangrove, jungle, cherry, sea, with the ice ones kept. Fresh-world captures at 1920x1080: set `overrideWidth:1920` and `overrideHeight:1080` in the run dir's `options.txt` for the session, and restore the `.orig` copy after. Pick from a contact sheet, then read each candidate at full size: thin dark lines at a distant water edge show only there.
- Gallery: Modrinth takes JPEG quality 90, a 4K copy for the gallery and a 1920x1010 copy in `docs/listing/screenshots/`. CurseForge caps each image at 2 MB: check sizes first.
- Upload with `docs/listing/modrinth.py add-image`; `modrinth.py show` prints each image's full-size URL, embedded under the section it illustrates. After any `description.md` change, push with the script, read back with `python -X utf8 -I docs/listing/modrinth.py show`, and diff against the file.
- Modrinth status `processing`: the public API answers 404. Read through the token script before calling a 404 a bug.
- Compatibility lists only the packs and mods run for this release.
- Edit or upload only after the user validates the text. Push the listing that names a loader or a game version only after the publish jobs logged success, so the page never names a file the stores do not hold yet (1.2.0: the text went to Modrinth after the jars, 2026-11-24). CurseForge: the user pastes the page and the gallery himself; hand him the final `description.md`, the JPEG paths and sizes, and the changed sections.
