# Farfield render perf probe

Measure renderer costs with a `// TEMP`-marked probe plus an A/B pack run, then revert the file (`git checkout -- <file>` only when the file has no other uncommitted work; otherwise copy back the scratchpad copy taken before the probe was inserted, because checkout would erase the uncommitted fix), confirm `grep -c TEMP` returns 0, and rebuild the clean jars before reporting.

- Read the `LOD renderer:` stat line and the `the longest LOD frame` breakdown in the pack's `latest.log` (needs `-Dfarfield.perfLogs=true`). Field meanings and the in-flight baseline: `references/stat-line-fields.md`.
- A/B: run the pack bench once per jar (HEAD vs working tree) on the same flight and teleport, minimized window, 3840x2019 override. Keep each jar and log under the scratchpad with a label per run.
- Noise floor first: bench the same jar twice (A/A) before a verdict. Two runs of one jar differed by 2.9% of pixels at 40 s, so a cross-jar gap of that size is not a change. Check each run's jar with `sha256sum` (the A/A copies must share one hash), and keep each run's `preview` folder under its label so the tiles can be compared byte for byte when the output must stay identical.
- A switch that is a runtime command (`/farfield debug prepass on|off`) needs no second jar: toggle it inside one run after the settled screenshot, wait about 25 s after each toggle, and read the GPU and CPU lines of each window from the log.
- Build the HEAD jar without `git stash`: it fails on untracked files (a new `.comp` shader). Copy the modified file to the scratchpad, `git checkout -- <file>`, build, copy the jar to `jars/head/`, copy the work file back, then `git diff --stat` must match the stat from before. Confirm the two jars differ with `sha256sum`.
- A bench runs about 7 min solo and about 15 min as an A/B. The Bash tool stops waiting at 600000 ms and moves the command to the background: put the runs in a `.sh` file, start it with `run_in_background`, and read its output file when the completion notice arrives. Never start a second copy while it runs.
- Upload backlog: wrap the `done` queue poll in `uploadMeshes()` with counters (wait per mesh, frames cut by the 3 ms budget, quads per frame). Remove them with the file checkout, not by hand.
- New-world scenario (the spawn, the LOD front as the view fills): a Rehearsal command file whose first line is `world <name> create <seed>`, then `look 0 5`, `screenshot <name>-02`, `wait seconds 3`, more screenshots, `quit`. The verb form is `world <name> [create <seed>]`, from the Rehearsal README. Run it with `fabric_pack.py` from the `rehearsal.dir` in `local.properties`: `--shader none --extension io.lakio.farfield.client.FarfieldRehearsal --jvm-arg=-Dfarfield.perfLogs=true --window minimized`, then `bash dev/rehearsal/run-commands.sh fabric/runs/prod <cmd file> 900`. Before the run, copy the pack's `options.txt` to the scratchpad, set `overrideWidth:3840`, `overrideHeight:2019` and `fov:0.0` (fov 0.0 is the 70 of the reference runs), then restore the copy. Delete `saves/<world>` before each run so every run starts from a fresh world, and kill the leftover `java.exe` whose command line matches the run dir.
- Fill A/B for a new world (ADR-152): put `command gamemode spectator` before `tp 0 200 0 0 12`, so the view is the horizon and not the player's own hole. Read both fill lines with `grep -a -E "Noise preview fill after joining|LOD view fill after joining" latest.log`: compare `sections missing in view` at 1, 2, 5 and 10 s, `view settled at`, and `meshes uploaded`. Pair the numbers with screenshots taken at the same seconds (`screenshot-ab-compare`). One run per jar showed a gap this size (651 against 398 missing at 1 s); smaller gaps need more runs, as `farfield-lod-hole-triage` says.
- Match the user's own game settings before a bench verdict counts. The run dir's default of 4 chunks of view hid the generated ring that the server builds past the game's view (ADR-154: the user's 12 chunks showed holes, the 4-chunk bench showed none). Set the game view per run with the server's `view-distance` and check the log line `Changing view distance to <n>, from <m>`: 12 chunks for the user's vanilla case, 32 for the worst case. A band the user reports at a small view (4 chunks) can be off screen in the 12-chunk bench: when the report names a small view, reproduce at that view too, with the shipped jar first. Set `fog_distance` and `fog` in the run's `options.txt` the same way as the user's config (the reference runs use `fog_distance=33554432`, `fog=false`), and grep the log for the chunk count to confirm each run used it.
- Sweeping a `-D` switch across bench runs (ADR-155 ratio sweep): do not edit the rehearsal script. Copy it to the scratchpad and add the hook after the ZGenerational flag: `sed -e 's/--jvm-arg=-XX:+ZGenerational/--jvm-arg=-XX:+ZGenerational ${EXTRA_JVM:+--jvm-arg=$EXTRA_JVM}/' newworld-rd.sh > newworld-k.sh`, then loop `EXTRA_JVM=-Dfarfield.<switch>=<value> bash newworld-k.sh 12 <label>` in one `.sh` file run in the background. Check `grep -c EXTRA_JVM` returns 1 before the loop, and keep the switch out of the tracked files.
- Flight A/B for a change to the pack's new-world flight: copy each jar into `jars/<label>/` in the scratchpad, then run every round from one `.sh` in the background, alternating ref and new (`fr1 fn1 fr2 fn2 fr3 fn3`) so load drift lands on both sides. Three rounds of two jars took about 40 min. Tell the user the duration and get a go first: the PC must stay free, and a build during a round shares the CPU with the game. Read code while it runs; do not build.
- The flight's flash probe needs `-Dfarfield.frames.dumps=400` on the run dir: the default of 20 dumps per minute caps it (`FrameProbe.MAX_DUMPS_PER_MINUTE`).
- Profile a bench with JFR next to the log lines: start each recording on the already-running JVM with `jcmd <pid> JFR.start name=bench settings=profile`, then dump it to `<scratchpad>/jfr/<side>-<pid>.jfr` with `jcmd <pid> JFR.dump name=bench filename=...` before closing the game. Never set `JAVA_TOOL_OPTIONS` on a `gradlew` run: it breaks Gradle's JDK 21 detection and both runs stopped after 13 to 14 s (2026-11-15). Read each file with `jfr print --json --stack-depth 64 --events jdk.ExecutionSample`, then count self time per thread group and the time under `farfield` frames. The `jfr` tool ships in the JDK 22 bin folder. To find who calls a hot method, run `jfr print --json --stack-depth 8 --events jdk.ExecutionSample` from Python with `encoding="utf-8", errors="replace"`, keep the samples whose `sampledThread.javaName` contains the thread group (for example `farfield-mesher`), and `Counter` the three frames that follow the first frame matching the method. One such run showed `725 PreviewLayer$2.maskAt:1416 <- PreviewLayer$2.real:1395 <- PreviewVoxels.build:399`, which located the per-column lookup before any edit.
- Config swaps in a bench `.sh`: copy `server.properties`, the client's `options.txt` and `config/farfield-client.properties` to the scratchpad, `sed -i` the keys for the run, and put the restore in `trap restore EXIT` so a failed or killed run still leaves the run dirs as they were. Grep the keys back before the run.
- Pack server config on the self-hosted server: do not guess its data path. The data dir is the host side of the `/data` volume in the server's compose file (the machine-local deploy skill names it). Read the `volumes:` line first: the compose folder's own `data/` does not hold `server.properties`.
- Before reporting, rebuild with `./gradlew.bat build --no-daemon -q -x test` and check `git status` shows no leftover changes.
