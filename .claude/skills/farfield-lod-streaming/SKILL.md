# Farfield LOD streaming (ADR-068)

A client joined to a server with Farfield draws the server's LODs, mirrored locally, and never builds its own. Keep these invariants when touching the streaming path.

1. **Gate on the join, not the session.** `StreamClient.streaming(mc)` is true from the join on, before the stream session opens, so client mode never starts. It is false in single player and on a server without the channel (`Services.NETWORK.serverStreams()`), or once the server declined.
2. **Tick order: stream first.** On both loaders `StreamClient.tick` is registered before `LodClient.tick`. Reversing it lets client mode build for one tick.
3. **Provider precedence.** `LodWorldProvider` returns, in order: the integrated server's store (single player, LAN host), the streamed mirror, then the client's own store.
4. **Mirror first, cache second.** The renderer asks the stream for a section it lacks (`needsFetch`, `want`). A stale local copy stays drawn meanwhile. `sectionExists` reads the server's region index, not the local cache.
5. **Index arrival reselects.** When region indexes arrive the stream generation changes; the renderer must mark the selection dirty so newly listed sections get requested.
6. **Check with a dev server and a dev client.** A run on 2026-10-25 (Fabric, the test world copied into `fabric/runs/server/farfield-test`, `level-name=farfield-test`, `online-mode=false`, client `-PquickPlayServer=localhost:25565 -PclientUsername=Dev`) streamed 10,188 sections at the 1,024 KB/s cap, view settled at 24.6 s. Read: server `LOD streaming to <player>`, the 10 s `LOD streaming: ... KB sent` lines; client `LOD streaming from the server`, `... KB received ... in flight, ... wanted`, and the mirror's `closed: N sections held`. A tiny server world (49 chunks) proves the protocol only: use the test world for numbers. NeoForge and two clients are not checked yet.

7. **Surface only by default.** `StreamServer` filters each region index through `SurfaceIndex` (first solid voxel from the sky per voxel column; sections whose top is under the column's floor are left out) and refuses direct fetches of hidden sections. `full_data=true` in `farfield-server.properties` sends everything.
8. **Preview tiles stream like sections (ADR-068).** Messages `TILE_FETCH`, `TILE`, `TILE_ABSENT`, `TILE_UNCHANGED`, `TILE_CHANGED`. A tile travels as its stored file (`PreviewStore.readFile`, `writeFile` on the client, which checks it decodes first). Its version is the CRC32C of that file (`PreviewStore.version`): `XxHash32` is package-private in `core.anvil`, so do not call it from another package. The client keeps `tiles.bin` beside the mirror, asks for tiles within the radius nearest first, at most 8 in flight, scanning once a second (`TILE_SCAN_NANOS`), and asks again when `TILE_CHANGED` arrives. On Windows, moving a tile file over the old one can fail with `AccessDeniedException` while a preview thread still reads it: `PreviewStore` retries the move for a moment. Keep that retry when touching the write path. The tile build is in `farfield-noise-preview`. A dedicated server builds the preview only when `preview=true` (default) in `farfield-server.properties`; `LodServer` reads that through `StreamServer.streamsPreview()`, so `StreamServer.onServerStarting` runs before the `LodServer` is made. The client asks for tiles only when its own `noise_preview` setting is on (the Fabric dev client's `config/farfield-client.properties` has it off: turn it on for a preview run, then back). To see the preview in a capture, put the dev client high (`gamemode spectator Dev`, `execute as Dev at @s run tp @s ~ 220 ~ 0 12` on the server console); at spawn a tree hid the view.
9. **Bump `StreamProtocol.VERSION` when a message changes shape.** Peers with another version are declined: a server answers a hello of another version with a refusal (a welcome of session -1 carrying its own version, ADR-070), and the client builds its own LODs instead of waiting; a client also gives up after 6 hellos without an answer (a server from before ADR-070). The tile messages moved it from 1 to 2, the welcome's table sizes to 3, `CHANGED` to 4, `HINT` to 5 (ADR-075). Every bump declines the clients still on the previous jar, so a deploy must name them (`farfield-home-server-deploy`). To check a change, compare a capture of the same view against a full-data run: the 2026-10-25 runs matched to 8 levels of 255 while sending 42 % fewer bytes.
10. **The mirror's key tables are its own (ADR-070).** The client keeps the server's keys in id order (`KeyTranslation`, `server-block-states.txt` and `server-biomes.txt` beside the mirror) and the writer thread `farfield-stream-mirror` translates each received section and tile (`remapIds`) before storing it; the hello announces the server keys held, never the table's size. Never write a received record into the mirror untranslated unless its ids map to themselves. To check a translation, add a key of the client's own to the mirror's `block_states.txt` (client stopped), make the server write an unknown block (`fill` near the player), then read a copy of the mirror (`farfield-mirror-probe`): the section names the real block, never the client's key; the stat line counts `translated`, the close line the keys of its own. A server of another protocol answers with a refusal (welcome of session -1, its version in the radius): to check, start the dev server, then set `VERSION` to 99 and start the client (the constant is inlined, the server keeps its own); put it back after.
11. **The preview reads real terrain at the top level, and the renderer never asks for it near the player.** `PreviewLayer.readMask` takes each tile's ground and fluid from the real top-level sections (`LodWorld.LEVELS - 1`) and hides the preview where real terrain is. The renderer draws finer levels close to the player, so those sections were never streamed there, and the preview drew over real terrain (water blended twice, preview grass over real sand). `StreamClient` fetches every top-level section of the radius in the background (the `background` queue, served after the renderer's wishes; index arrival fills it, a session reset clears it, a new selection does not). Keep that queue when changing the wishes. A render bug only seen when streaming: compare with the same view after this fetch, and read a copy of the mirror from a temporary test (`farfield-mirror-probe`), never the live store, before suspecting the stored light.
12. **Change notices and the fetch window (protocol 4).** `StreamServer` listens to each streamed world's section writes and keeps them per region (`RegionChanges`: a region is announced once quiet for 3 s, or at most every 20 s while an import keeps writing it; since ADR-075 the pipeline writes a section idle for 250 ms (not 3 s) and item 15's pushes carry the in-range levels, so the notice covers what is not pushed); once a second it sends `CHANGED` to the players near a due region. The client asks those indexes again, only for regions it knows or asked for; the renderer then fetches what moved. Requests in flight follow `FetchWindow` (AIMD, 4 to 64, halved when an answer is 1 s later than the quickest); tile requests have a window of their own (1 to 16): a tile weighs about six sections. Cost check: the server's `LOD CPU usage over 60 s` line gives a `stream` figure apart from the worldgen categories; 0.1 s per minute with 5 to 15 regions changing per 10 s is the reference (NeoForge run, 2026-10-26), so compare against it before optimising. After a test, restore what you changed: `lod_rendering=false` in the dev client's `client/config/farfield-client.properties`, the moved-aside `farfield-test/farfield` store, and delete any second client run dir. To check notices, start a dev server with an empty store (move `farfield-test/farfield` aside, put it back after), join, then `farfield import`: the client's stat line counts `regions changed` and its sections grow without reconnecting; a rejoin afterwards should fetch almost nothing. A client whose saved position is outside the imported area gets nothing new: teleport it first. The dev client's `lod_rendering` may be off: without the renderer no index is ever asked (0 known regions). To check the window, set `player_kbps=64`: the stat line's `in flight of N` falls to 4, then grows back. A second Fabric dev client: start one with `runClient`, then the same JVM command line (from `Win32_Process`) with `--username Dev2` and another working directory.
13. **An index refetches what the mirror holds at an older version.** The renderer asks only for sections it lacks, so a drawn copy fetched while its chunks were still generating stayed drawn: black 32-block holes over new ocean (a surface section missing a chunk the section under it had), seen from the user's server on 2026-10-27. `StreamClient.index` puts every held key whose version moved into `background`; the stat line counts `outdated`. Check: teleport a dev client over new ocean (`locate biome minecraft:deep_ocean` from far away), wait 2 min, capture; a rejoin of an old mirror shows `N outdated` at once.
14. **New terrain comes in coarse first, never as a hole (ADR-074).** A split parent keeps splitting over a child that is not ready only if its mesh draws nothing in that child's octant (`Resident.octants`, `LodSelector.Sections.octants`); a drawn copy older than the server's is marked stale at selection so it is fetched with the wishes, not after the background queue. Do not bring back the unconditional "keep descending": on a mirror the coarse levels and the preview's level-4 mask arrive first, so the parent does show the new child's area. Latency figures: server line `written regions announced N ms after their first write`, client stream line `outdated sections refreshed N ms after their index`, renderer line `outdated sections drawn per selection`.
15. **The server pushes what it writes (ADR-075, protocol 5).** The store listener queues each written section for the players whose client draws its level there (`StreamServer.pushRange` from the client's `HINT` detail; level 4 in the whole radius), in write order so children go before parents; `startPush` reads them when the player's queue holds fewer than 64 messages. Pushed level-0 sections must pass `SurfaceIndex.hidden(key, floors)` (anti x-ray, ADR-013): never push from a path that skips it. The pipeline writes sections idle for 250 ms, every 250 ms. A refreshed coarse index makes the client ask the finer region's index again, only for a region it already knows: a region read for the first time moves nothing the renderer relied on (a guard, not a fallback to remove). Figures: server `sections pushed N ms after their write`, client `N of them pushed`, `finer indexes asked again`. Next step if still slow: push from memory with content-hash versions.
16. **No artificial waiting on the stream path.** A hold, batch or quiet window is latency the player feels as lag, and the user refused a 3 s hold before a push because it breaks immersion (2026-10-28). Keep only the batching a measured cost requires (the 250 ms write batch is the ceiling), and state the figure that justifies any new delay before adding it. Ask the user before keeping one.
17. **Read the predecessor first when a mechanism was tuned there.** The user spent long tuning Neo-Voxy's streaming (server `LodStreamingService`, client `LodReceptionService`). Before proposing a streaming design, read that implementation and reuse its concepts; never copy its code (ADR-001).
18. **Coarse levels: new chunks first, a rebuild only when idle, mirrors never rebuild (ADR-083).** A `MIPS_VERSION` rebuild has its own queue, every level queued, finest first, and runs only while no chunk is being ingested, none waits to be written and nothing live is dirty (batches of 256, 50 ms a pass). The user's rule: "Si on a des chunk neuf a traiter on le fait, sinon on fait la maintenance". A mirror (`LodWorld.openMirror`) never builds coarse levels: built at close from its partial level 0, they replaced the server's and held a client for 46 s. Each mirror forgets its held coarse versions once (`coarse.v1` marker), so they are fetched again. The rebuild writes `MIPS_VERSION` only at its end: a server restarted mid-rebuild starts it over. Check: a client's first join logs `coarse levels are fetched again from the server, once`, and server pushes stay at tens of ms during a rebuild.
19. **A pushed section is meshed once, after the mirror stores it (ADR-086).** `StreamClient.storing(key)` stays true from the receipt until the mirror's writer has stored the record; the renderer keeps such a key in `waitingStore` and selects it once `storing` is false. Meshing it earlier made nearly every pushed section mesh twice, with the preview held over it in between: the overlap the user saw. Keep ADR-085's second mesh only for a section written while its mesh is in flight. Not yet checked in game. ADR-088 narrows the hold: a section waiting for a new mesh holds the preview over a chunk only where its drawn mesh has nothing in that chunk's column; a section that already draws the column does not hold it (at a generation front, every section beside new chunks is meshed again for each of them, so the old rule kept the preview over drawn terrain).

Renderer details: `farfield-lod-renderer`. Launch and log reading: `farfield-dev-client-check`.
