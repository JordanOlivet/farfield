# Farfield dev client check

Judge a dev client run from the game log and a screenshot, never from the Gradle output. The Gradle log is overwritten by the last run and is not the game's log.

1. Ask the user right before every launch, with AskUserQuestion, and wait for a yes. A scripted client takes over their Windows session (focus, keys, window), and they may be watching a video or working. Each launch needs its own yes, except a series the user grants in one AskUserQuestion answer that names the task and its runs (answered "Oui pour la série" for a 5-biome bench of one task): those runs cover that task only, each launch is announced in chat before it starts, and the grant ends with the task. A user who says in the session that they are away from the PC (not using it) grants the launches of the task in progress without asking; still name each launch in chat, and stop as soon as the user says otherwise. These do not count as one: a yes to an earlier launch in the same session, a plan or time estimate that said "dev test included", a "vas-y" to implement the change, or a relaunch after a fix. If the user says no or does not answer, do not launch: commit, copy the jars, and hand the test to the user. A message sent mid-turn that says not to launch ("ne lance pas le client sans me demander, j'utilise le pc") cancels any launch planned in that turn, even one the agent had already started to prepare: stop, and ask with AskUserQuestion once the build is green.
2. Before starting, sweep leftover farfield JVMs (exclude Gradle daemons, see CLAUDE.md) and delete `session.lock` in the world save of the run dir (`fabric/runs/client/saves/<world>/`, `neoforge/run/saves/<world>/`), and the dev server's `session.lock` too (`fabric/runs/server/farfield-test/session.lock`) before each server start: a killed server leaves it behind, and scripted runs delete it first. A stale lock blocks the world. Also count the Minecraft windows (`java` processes whose `MainWindowTitle` starts with `Minecraft`). Any one open means abort: a launch over an open client left three windows, and the focused one sat on the title menu, not the world.
3. Start with `-PquickPlay=<world>` in the background, Gradle output to a scratch file. A background task reported as `failed` with exit code 127 does not mean the client is down: twice in one session the task notification said failed while the game log kept updating from a live client. Read the game log's last timestamp (`stat -c %Y`) before relaunching, and never start a second client on the same world. To wait for the game to be ready, loop on the log: require its mtime to be at or after the launch time, and end on the ready line (`sections drawn`), `LOD rendering disabled`, or `Crash` / `Exception in`, so a crash also ends the wait. A screenshot taken after a `failed` launch shows whatever window was already open, not the new build: it is no evidence for a fix until a `sections drawn` stat line newer than the launch appears in the log. Report it as unverified otherwise.
4. Read the game log at `<run dir>/logs/latest.log`. A new run overwrites it, so read it before starting the next run. For a real modpack install, read the instance folder's `logs/latest.log` instead. Use `grep -a`: the logs contain NUL bytes and plain `grep` reports "Binary file matches".
5. Read the result: a `LOD rendering disabled` WARN means the path did not run. A `LOD renderer: N sections drawn` line with N > 0 means it did. The stat line comes every 10 s (30 s before 2026-10-25). In a user's pack it is off unless the performance logs setting is on (Mods > Farfield > Config, or `-Dfarfield.perfLogs=true` on a dedicated server); the dev Gradle runs set it, so a pack log with no `LOD renderer:` line means the setting, not a crash. When comparing settings (`/farfield detail <px>`), wait for two consecutive stat lines that both show `0 meshing` before capturing: a capture taken during meshing shows a half-loaded scene and the numbers from that line are not steady state. A polling loop over the log with `grep -ac "sections drawn"` counts new lines reliably.
6. Maximize the window (Win32 `ShowWindow` 3) once it appears: the user watches the run and the default window is too small. Capture it with `PrintWindow` (flag 2) from a DPI-aware process, then read the PNG. Check a night shot as well as a day shot.
   - Renderer first: a dev client without Sodium draws vanilla terrain only. Before a second fix to a render effect, ask which renderer the user's pack runs. A bug that shows only on the vanilla path may not exist in a Sodium pack, and then the fix belongs to the vanilla path alone. Say so in the report instead of calling it a regression.
   - Sodium checks: the Sodium jar may already sit in `fabric/runs/client/mods` as `sodium-fabric-<ver>.jar_disabled`. Enable it by renaming it to `.jar` before the launch, then rename it back to `_disabled` after the check and confirm with `ls fabric/runs/client/mods`. Do not leave a copy beside it, and never leave the jar enabled for the user. Without an enabled jar the Fabric dev client runs vanilla rendering. For a Sodium run, also grep the log for `Mixin apply failed`; no match is part of the proof.
   - Chat commands: focus the window, send the chat key, the text, then Enter. The user may rebind it: read `key_key.chat` in the run dir's `options.txt` first (seen: `key.keyboard.enter`, so "t" did nothing and the digits of a `/tp` switched hotbar slots). Never send Escape to close a stray chat: with no chat open it opens the game menu, which eats the next keys. `SetForegroundWindow` silently fails from a background process: press and release Alt (`keybd_event` 0x12) first, then check `GetForegroundWindow` before typing, else the keys go elsewhere and the log shows no `[CHAT]` line. Export `MSYS_NO_PATHCONV=1` in Git Bash, or `/tp` becomes `C:/Program Files/Git/tp`. `~` is a dead key on the user's AZERTY layout and eats the next space: write `~  ` (two spaces). `^` is worse: `/tp @s ^ ^ ^3` arrived as `/tp @s 6 6 63`, an absolute teleport underground, repeated by a loop until the user stopped the client. Never send `^` coordinates; step with absolute coordinates computed in the script, and never loop chat commands without reading the `Teleported` line after the first one.
   - LOD textures: `/farfieldclient textures 0` turns them off and `/farfieldclient textures all` restores the default. The reply is logged as `[CHAT] LOD textures on every LOD`. Check that `texture_distance=all` is back in the run dir's `config/farfield-client.properties` after the check.
   - Clouds stay off in both run dirs' `options.txt` (`renderClouds:"false"`, the user asked): at the camera heights used for LOD shots the camera sits in the cloud layer (y about 190) and the frame washes out white. Check the line is still there if `options.txt` was regenerated. The value is a quoted string: `grep -n renderClouds <run dir>/options.txt` first, then `sed -i 's/^renderClouds:.*/renderClouds:"false"/'` when the line exists. A run dir may have no such line (the Fabric one had none): append it with `printf 'renderClouds:"false"\n' >> <options.txt>`. Run dirs are gitignored, so the change stays local.
   - Killing the JVM while the game saves its settings can truncate `options.txt` to a few lines (seen: 6 lines, `renderDistance` and `pauseOnLostFocus` survived, the rest was lost). After any kill, check the line count (`grep -c "" <options.txt>`) and restore the missing keys before the next run; the cloud line is the one this skill depends on. Line 1 must be `version:<n>`: without it the game reads the bindings in the old numeric format and drops the whole file, so the Farfield settings key (F7, bound in the NeoForge run dir only) vanishes too. Check `head -1` and restore `version:3955` when it is missing.
   - Client settings (`config/farfield-client.properties` in the run dir) survive between runs. After a run that changed one, put the default back before the next run, then read the `LOD settings loaded from farfield-client.properties` line of that launch: its values are the ones in force. Check with `grep -a "LOD settings loaded" <run dir>/logs/latest.log | cut -c1-200`.
   - Structures in the preview (villages): `/locate structure #minecraft:village` prints the nearest one in chat and the log (`The nearest #minecraft:village ... is at [x, ~, z]`). View it with `/tp` about 230 blocks away, so its real chunks stay unloaded and the preview tile shows. Allow about 35 s for the tile before the capture.
   - Benchmark runs: send no keys to move the player. If no server-side move exists for the view you need, add a temporary local hook (never committed) that teleports the player after the world loads, and read its `Bench` log line before capturing. Launch with `JAVA_TOOL_OPTIONS=-Dfarfield.benchTeleport=x,y,z` (a temporary dev switch, removed with the measurement); the server moves the player and logs `Bench teleport of <player> to x,y,z`. Grep that line before reading any timing. Keyboard moves failed silently once the user's bindings differed from the script's.
   - Finding a bench spot: a temporary server-tick hook (never committed) calls `ServerLevel.findClosestBiome3d(...)` from the player, then counts a target block per chunk with `level.getChunkSource().getChunkNow(cx, cz)` and teleports to the densest chunk. Log the block classes under test (`BlockKeys.resolve(BlockKeys.key(state))`) from the same tick, so the log shows what the renderer classifies. Hook it with one line in `LodServer.onServerTick`. A bench that visits several biomes runs as one launch: the hook teleports per phase and logs a `Bench shot <name> <kind>` marker at each shot; the runner polls the log for new markers and captures one PNG per marker, then stops on `Bench done`. Read the top block of a column through `WORLD_SURFACE - 1` (the heightmap value is the air above it), so a double plant counts once. Before any commit, remove the hook line and the bench file: `git status` must show neither.
   - A bench writes into the run dir's test world. Snapshot the save with `robocopy /MIR` before the first launch, restore it before each config, and restore `options.txt` and `config/farfield-client.properties` from `.orig` copies at the end. Run one client per config from a runner script that waits for the bench's marker line on the log (mtime at or after the launch), captures, then closes the window and sweeps the JVMs before the next config.
   - Far teleports: before any `/tp` beyond a few thousand blocks, read the save's world border. `level.dat` is gzip NBT: `BorderSize` (a double, the side length) and `BorderCenterX`/`BorderCenterZ`. Outside the border, a player in survival or adventure loses 0.2 HP per block beyond the 5-block margin and dies at once from a teleport 8,000 blocks out. Creative and spectator take no border damage, so the death shows only after the switch to adventure. The log says `left the confines of this world`, and a red vignette appears first. Keep test teleports within BorderSize/2 of the center, or enlarge the border with `/worldborder set` before the teleport.
- Confirm a `/tp` ran before capturing: `grep -a "Teleported" <run dir>/logs/latest.log | tail -1` must show the target. A teleport that did not run leaves the view on the world's last saved position, which looks like a valid capture and compares nothing (seen: desert shot taken as the lake).
   - Scripted repro of a border case (a pit beside real terrain): `/fill` the air, then the water, and confirm each `Successfully filled N block(s)` line in the log before the capture. Read the loaded area first: a pit dug at the edge of the loaded chunks fell in open sea once and in real forest once, so the loaded area is wider than the radius assumed. If the pit does not sit where the case needs, the capture reproduces nothing; say so and leave the case to the unit test or the user's pack. After a `/tp` to new ground, allow about 45 s for the preview to build before capturing.
   - Settings screen: read every row in the full-resolution capture and check that each label shows its caption once. A cycle button that adds its own caption, next to a value text that repeats it, showed `Dimension Fog: Dimension Fog: Pushed Back`. After a fix, check the label in a fresh launch, since the saved value only shows after a relaunch.
   - Clicks: the screenshot you read is downscaled. The image notice gives the factor (`displayed at 2000x1081. Multiply coordinates by 1.93`); multiply the coordinates read off the image by it before passing them to `click.ps1`, then capture again to confirm the click landed.
   - The test world `farfield-test` keeps `doDaylightCycle false` at noon; `/locate biome` finds temperate areas (the spawn is snowy). Its seed, rules and known places are in `docs/test-worlds.md`; cite coordinates of that world in reports, and add a row there for a new place worth a look. A missing save is copied from `dev/` at the next launch.
   - Night shot: `/time set midnight`, wait about 5 s, capture, then `/time set noon` to put the test world back. The LOD half and the vanilla half of one frame must share the same light.
   - Water and ocean shots: put `weather clear` in the pre-capture commands before any capture, both sides of an A/B. Rain on the view made one capture unreadable and forced a rerun. For a sea-floor A/B, `/locate biome minecraft:deep_lukewarm_ocean`, teleport high (y about 110 to 150) with pitch about 30 so the preview sea is in frame, and capture with the preview setting on and off, or with the fix on and off, at the identical position. To reach an ocean the mirror has not filled: `execute positioned <x> 100 <z> run locate biome minecraft:deep_ocean` on the dev server, read the `The nearest minecraft:deep_ocean is at [x, 100, z]` line in its log, then `tp Dev <x> 140 <z> 0 25` on the client. Allow about 2 min for the fill before the capture. Compare A/B only within one session at one position: a capture from another session differs in the far band because its fill was not the same, so it proves nothing.
   - Screenshots reach `Read` downscaled to 2000 px wide (the image notice gives the factor). For a detail check, crop the region from the full-resolution capture with System.Drawing (`InterpolationMode` `NearestNeighbor`, `PixelOffsetMode` `Half`, scaled 2x) and read the crop, so the pixels are not resampled twice. For a seam or a distant-terrain judgement at the horizon, crop only the band around it (full width, rows 560 to 1220 of a 3866x2090 capture, halved to 1933x330 with `Pixel` mode) and capture the same view with the setting on and off, so both bands are read side by side.
   - Quick LOD check: set `renderDistance:2` in the run dir's `options.txt` before the launch to load vanilla chunks fast. Once the check is done, restore the original value (`renderDistance:8` in `fabric/runs/client`) and read it back with `grep -n renderDistance`.
   - `/farfield debug levels` toggles the level colors (single player; a client joined to a server uses `/farfieldclient debug levels`, and the same holds for every drawing setting: `render`, `detail`, `textures`, `fog`, `preview`, `debug`); the chat reply names the palette (red 1 block, orange 2, yellow 4, green 8, blue 16). Send it once to turn the colors on, capture, send it again to turn them off, and check the `LOD level colors on` and `off` replies in the log.
7. After the run, stop the client and sweep the JVMs again. A killed Gradle leaves the game JVM running. A stopped background task (TaskStop) kills only its shell: its runner script and the game JVMs it started keep running and open more windows on the same world. Stop the runner and its children together, then list the game JVMs (see the global `background-process-sweep` skill). Stop the game with `CloseMainWindow` on the `java` process whose title starts with `Minecraft`, wait about 15 s so it saves `options.txt`, then sweep; a hard kill during that save is what truncates the file.
8. Client mode runs (the client joins a remote server without Farfield): start `.\gradlew.bat runVanillaServer --no-daemon --console plain` in the background with its stdin scripted like the dev servers, and wait for its `Done (` line. To prove the client ingested chunks, delete the run dir's `farfield/servers` folder before the launch, since that store is kept per server address and seed and a kept store makes a fresh build look like a cache hit. To prove persistence, keep the folder and relaunch. Read `Client mode: building the LODs of` at join, `LOD store of ... (client) opened`, the `LOD renderer: N sections drawn` stat line, and at Disconnect or quit `LOD store of ... (client) closed: N chunks ingested`. Read these with `grep -a`, and check the run's first and last timestamps to tell the new run from the old one. Stop the vanilla server only after the client is closed: `Stop-Process` on the `java` whose command line matches `server.jar nogui`.

9. Chat command runs (`/farfieldclient ...`): grep the reply text, not the log prefix. Fabric logs `(Farfield)` and NeoForge logs `[Farfield/]`, so `grep -a "Remote world"` matches both. After a command that moves a store, the `LOD renderer: N sections drawn` count must come back to the N it had before the move. A count that falls to 0 means the reopened store did not load from disk. Run the same command on both loaders before calling it verified.

10. Dev server + dev client runs (a client joins a Farfield dev server): the dev server reads stdin, so feed it commands through a file kept open with `tail -f <cmdfile> | ./gradlew.bat :fabric:runServer --no-daemon --console plain`, then append `farfield import` or `stop` to the file. Wait for `Done (` in the server's `logs/latest.log` before sending commands, and for `LOD import of ... done` before launching the client. Check `online-mode` in the server run dir's `server.properties` first: `runServer` copies that file once and never overwrites it, so the default `online-mode=true` (seen in `fabric/runs/server`) rejects an offline dev client until it is set to `false` once by hand (`sed -i 's/^online-mode=true/online-mode=false/'`). The `dev/server` template already has `false`.
   - Measure a fill from the client log, not by eye: `grep -a "LOD view fill after a teleport"` gives the sections missing in view per second and the settle time; `grep -a "LOD meshing:"` gives the mesh jobs per stat line. Compare two builds at the same view by their job totals and settle time. A job count inside run-to-run noise is no cost.
   - Before the client launch, wait for both logs: the server's import line and the client's `sections drawn` stat line. The client must be a `runClient -PquickPlayServer=localhost:25565 -PclientUsername=Dev` launch. Read the streaming lines of both sides with `grep -a`; a server with the stream feature sends sections to the client, and a client that builds its own LODs in the same run is a bug, not a pass.
   - A fix to how chunks are ingested does not change stored LODs. Before the check, delete the world's `import.checkpoint` (the LOD dir under the save, e.g. `fabric/runs/client/saves/farfield-test/farfield/import.checkpoint`), or the import skips regions already marked done, then run `/farfield import` and wait for `LOD import ... done`. Also the same re-import is needed on the user's server and in his pack copy.
   - Stop the client window with `CloseMainWindow`, wait about 15 s, then send `stop` to the server file and sweep the JVMs. Append the `stop` from Bash (`echo stop >> <cmdfile>`). A PowerShell `Add-Content` to the same file failed with a sharing violation while the server held it, and the server was then force-killed. A force kill skips the LOD store close, so the counters `stop` logs are lost: wait for that line in the server log before sweeping. The `CloseMainWindow` filter on `MainWindowTitle -like 'Minecraft*'` reaches only the client, since the dev server has no window.

## Pack run: the user's pack beside the dev build (ADR-097, ADR-098)

`.\gradlew.bat :neoforge:runPackClient -PquickPlay=farfield-test -PfreshWorld -PagentWindow=minimized` loads the dev build among the mods of the pack instance named by `farfield.pack.dir` (local.properties), in `neoforge/runs/pack`. It takes about 80 s to the agent inbox and 10 GB of heap.
- `syncPackMods` mirrors the pack's jars on every run (Farfield's own jar and Crash Assistant left out); configs, kubejs, resource and shader packs and `options.txt` are copied once, missing files only: delete one in `runs/pack` to take the pack's again. Disable a mod for an A/B by renaming it in `runs/pack/mods`, and remember the next sync puts it back.
- `-PfreshWorld` deletes the save first (LOD store included): the open bug shows only over terrain never generated, so use it for every repro run.
- The dev NeoForge is the pack's (21.1.248): when the pack moves, move `neoforge_version` too, or its Forgified Fabric API refuses the run.
- Connector needs `-Dconnector.clean.path` (the run passes ModDevGradle's `vanilla-deobfuscated.jar`). Without it the Fabric mods are refused, NeoForge logs `Cowardly refusing to send event ... to a broken mod state`, and the client crashes later on an unrelated mod ("Registry is already frozen"): read the first error of the log, not the crash's.

## Agent inbox: drive the client without keystrokes (ADR-095)

Prefer it to every keystroke and `click.ps1` step above: no focus, no chat key, no AZERTY trap. The dev client runs of both loaders set `-Dfarfield.agent=true`; a pack instance needs it added to its JVM arguments.

1. Launch as usual (consent, sweep, `-PquickPlay`), plus `-PagentWindow=minimized` (ADR-096): the window opens without the focus, never grabs the mouse, and goes to the taskbar, so the user can keep working; `background` puts it behind the other windows instead. Both still draw (screenshots are fresh while minimized). Skip the maximize step of point 6 for such a run: `ShowWindow 3` activates the window. On NeoForge the run turns FML's loading window off in `run/config/fml.toml` and puts the file back when Gradle ends; after a killed Gradle, check `earlyWindowControl = true` there and copy back `fml.toml.agent-saved` if it is still beside it. Wait for `Agent inbox on: <dir>` in the game log, never before: opening the inbox deletes the command files already there.
2. Write the commands to `<run dir>/farfield-agent/inbox/<name>.tmp`, then `mv` it to `.cmd` (only `.cmd` is read, files in name order). One per line: `command <text>`, `tp <x> <y> <z> [<yaw> <pitch>]` (absolute numbers only; `~` and `^` are refused), `look <yaw> <pitch>`, `screenshot <name> [hud]`, `state`, `wait stable [timeout] [hold]`, `wait ticks <n>`, `wait seconds <s>`, `window minimize|background|restore`, `record start <name>`, `record stop`, `replay <name> [speed <f>] [every <n>]`, `frames on|off`, `quit`. World commands wait for the player, so the file may go in while the world loads.
3. Read `<run dir>/farfield-agent/outbox.jsonl`: one JSON line per command with `ok`, and `error` when a line was refused. `screenshot` gives the PNG `path` (in `farfield-agent/shots/`, the game's own framebuffer at window size: maximize first for a detail check). `wait stable` gives `outcome` (`settled` or `timed out`), the seconds and the renderer counters; capture only after `settled`; `LOD rendering disabled` as outcome means the renderer is off (check the `OpenGL 4.6` lines) and nothing will settle.
4. Chat replies are not in the outbox: grep the game log for `[CHAT]`, as before.
5. End with `quit`: the game closes as from its own close button (no truncated `options.txt`), then sweep the JVMs.

Steps 1 to 3 in one go: `dev/agent/run-commands.sh <run dir> <command file> [timeout s]` (Git Bash, run in the background beside the client). Ready command files with their launch line and what to read: `dev/agent/scenarios/` (inbox smoke test, window out of the way, pack flight, replay and frame probe). The runner also copies the test flights of `dev/agent/flights/` into the run dir. To prove a run leaves the user's focus alone, start `dev/agent/focus-watch.ps1` beside it. It waits for the inbox, drops the file, waits for the `quit` reply (exit 0), and on a crash report in the game log (exit 2) or at the timeout (exit 3) closes the game JVMs this checkout started since it began (`dev/agent/close-game.ps1`): a mod loading failure leaves FML's error screen open and the client would never quit. It took 81 s on NeoForge for a spawn, a teleport, two settles, four shots and a level colors toggle (2026-10-29). Match crashes on `Crash report saved to`, never on `Crash`: the pack's Crash Assistant mod logs that word at every start.

## Flights and the frame probe (ADR-099)

- A flight is `<game dir>/farfield/flights/<name>.flight`: the user records one with `/farfieldclient record start <name>` and `record stop` in their pack, and sends the file; copy it into the run dir's `farfield/flights/` and `replay <name>`. A generated flight is plain text (header `# Farfield flight 1`, `dimension minecraft:overworld`, then `x y z yaw pitch` per tick). Put the player in spectator first, and use `-PfreshWorld`: the open bug shows only over terrain never generated.
- `replay` teleports to the start when it is more than 16 blocks away, then waits 2 s; `every <n>` saves `shots/<name>-<tick>.png` with the HUD hidden. Its reply gives `ticks`, `seconds` and `frameEvents` (the probe's events during it).
- `frames on` (or `/farfieldclient debug frames`) writes `farfield/frames/<session>/`: `first-background|lods|end.png` (check them once: sky, LOD pass, final image, right way up), `events.jsonl` (one line per event: `kind` flash1, flash2, erased or column, `frame`, `box` in capture pixels, `camera`, `examples` for columns), and the frames around each event as PNGs (20 events a minute at most). Read the stat line `Frame probe: ... in 10 s (... us per frame on the render thread)`: the probe costs frames, so compare fps only with it off.
- The events are not judged glitches: a replay compares builds by counting them over the same flight, N runs per build, since no two runs give the same frames.
- `gradlew :core:flashScan --args="<frames dir> --expect <frames> [--ignore-color 0070D0:90]"` scores the flash detector on a recording cut into images (last line: `score: N of M glitches found, K other frames flagged`). The user draws annotations on the frames (blue strokes, about 0070D0): take them out with `--ignore-color`, or the detector "finds" the strokes. The reference recording, its 18 annotated frames and the score to beat are in `docs/analysis/agent-playtesting.md` (Reference recording): rescore after any change to `FlashDetector`.

Rendering and lighting rules: see `farfield-lod-renderer`. Server-to-client streaming: see `farfield-lod-streaming`.

## Handing a jar to the user (pack test)

Hand a jar over only after the dev check passed and the jar is committed. The user's pack is the real check; the dev client is not.

1. Commit, then run `.\gradlew.bat copyTestJars --no-daemon`. It builds both loader jars into the `farfield.testJars.dir` folder of `local.properties` and deletes the older Farfield jars there. Check the two `Copied` lines and name that folder to the user.
2. Ask the user to close the game and copy his world. He tests the copy, never the live save.
3. Send a numbered procedure: which jar goes in which loader's mods folder, remove the older Farfield jar first, start the instance, open the copy. Run `/farfield import` and wait for the `LOD import ... done` line only when the change touches stored LOD data (storage format, downsampling). A render-only or settings change needs no re-import. A `MIPS_VERSION` bump rebuilds the coarse levels once at open: warn that the first open is slower, and judge the far view only after the `coarse levels rebuilt` line.
4. Name the views to check: distance by day and by night, F3 fps with LODs on and off (`/farfield render off` at the same spot), and the look of leaves and water.
5. Ask for the game log, not only screenshots. Performance lines are off by default since 2026-10-25: have the user turn on Performance Logs (Mods > Farfield > Config) or set `performance_logs=true` in `config/farfield-client.properties`; a dedicated server needs `-Dfarfield.perfLogs=true`. Read the import done line, the `LOD CPU usage` line, the `LOD renderer` stat line and the `LOD store ... closed` line with `grep -a`, from the instance's own `logs/latest.log`. For client mode, also read the `Client mode: building the LODs of` line at each join or dimension change and `Left the remote server`.
6. Say what stays unverified: the user's own flight and the visual quality. Fences, walls, panes and stairs are drawn since ADR-036 (2026-10-18), so they are not gaps.
7. End with one action for the user, such as "reply `fini pack N`". When he defers the test, the closing message restates the resume line: jar path, first step, what to report back. When he gives a verdict, tick the plan item it closes, quote his words in the progress log, and write any scope left out into the item.
